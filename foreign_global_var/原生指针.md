# 逐段深度解析这份 Rust‑FFI 官方文档
全文一共4大块，分别讲解 **结构体内存布局、Box/引用裸指针规则、Vec/String FFI注意事项、libc 依赖包**，专门用于Rust和C语言互操作。

## 第1段：`#[repr(C)]` 结构体内存布局
> Rust 默认结构体内存布局是**编译器自由优化**：字段顺序、内存对齐填充(padding)不确定，和C结构体布局不一样，不能直接传给C函数。

### 三个关键属性
1. **`#[repr(C)]`**
强制结构体按照当前平台 **C语言标准布局** 排布；字段顺序和你代码书写顺序保持一致、对齐规则跟随C标准，结构体就可以安全传给C代码。
```rust
#[repr(C)]
struct MyData {
    a:i32,
    b:u64
}
```
也能够挂载在 `enum`，让枚举布局兼容C。

2. **`#[repr(C, packed)]`**
`packed` = **取消内存对齐填充字节**
C语言默认会插入padding补齐对齐；packed 紧凑排布成员，没有空位填充。
> ⚠️ 未对齐内存访问在部分架构会直接程序崩溃，谨慎使用。

## 第2段：`Box<T>`、引用 `&T`、裸指针 `*const T` 的FFI区别
### 1. Box<T>
- 底层本质：**保证不为空的指针**，指向堆上的数据
- 硬性规则：**绝对不要手动构造 Box**
Box 由Rust内部内存分配器管理；手动裸指针强转创建Box，会破坏内存管理，引发内存释放、二次释放、内存泄漏。

### 2. 引用 &T / &mut T
引用同样一定是非空指针。
但是引用受 **借用检查、可变别名规则** 严格管控。
一旦你强行绕过借用规则、强行类型转换，代码就不再具备内存安全。

### 3. 结论：需要绕过安全规则 → 用原生裸指针`*T`
编译器会对 `&T`、`Box` 做大量安全假设（指针非空、别名规则、生命周期）；
裸指针不会被编译器施加这些硬性假设，做FFI、底层内存操作优先选用裸指针。

### 简单对比
|类型|是否允许空指针|编译器约束|适合场景|
|---|---|---|---|
|`&T`|禁止为空|借用检查、别名规则|常规安全Rust代码|
|`Box<T>`|禁止为空|堆内存所有权管理|安全堆分配|
|`*const T`/`*mut T`|可以是空指针|几乎无检查|FFI、底层裸指针操作|

## 第3段：Vec、String 和 C字符串互操作
1. `Vec<T>` 和切片 `&[T]`、`String` 和字符串切片 `&str` 内存布局兼容：指针 + 长度。
Rust标准库 `vec`、`str` 内置了一些适配C接口的工具函数。

2. **最常见坑点：Rust String 不带 `\0` 空终止符**
C语言所有字符串依靠末尾 `\0` 判断字符串结束。
所以**绝对不能直接把 `&str` 的指针传给C函数**，会造成内存越界读取。

### 解决方案（你之前接触过）
`std::ffi::CString`
它会在堆上分配字节缓冲区，自动追加末尾`\0`，适合传给C接口。
```rust
use std::ffi::CString;
let c_str = CString::new("hello").unwrap();
let ptr = c_str.as_ptr(); // *const i8，可以传给C函数
```

## 第4段：libc crate
1. crates.io 的 `libc` 包
提供各个操作系统C标准库的类型别名（`c_int`、`c_char`、size_t）、系统函数声明。
做FFI几乎一定会引入它。
```toml
[dependencies]
libc = "0.2"
```
2. Rust程序默认会自动链接系统动态库 `libc`（C标准库）、`libm`（数学库）。

# 整体FFI实操总结（适配你调用 libsnappy 的场景）
1. 传给C的结构体必须添加 `#[repr(C)]`；
2. FFI传指针优先裸指针，不要强行构造Box、篡改引用；
3. C风格零结尾字符串必须使用 `CString`；
4. C语言类型（`size_t`、c_int）统一使用 `libc` 包；
5. 外部函数块 `extern "C"` 使用C调用约定。
